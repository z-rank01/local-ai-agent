当前已有的“Recipe 雏形”

research.json 保存范围、计划与阶段；证据索引保存来源和实际收到的摘录；草稿、核对记录与检查点分别保存。

这些记录支持追踪，但还没有统一回答：“这一阶段用的是哪版材料？哪些内容进入了模型请求？上一阶段的疑点是否交给下一阶段？”

研究循环中的模型实际能看到什么？

主要输入：当前问题、可用会话历史、系统与插件提示、工具回执，以及循环注入的实际证据清单。

边界：下载保存的全文不等于已经向模型返回全文；旧的大工具回执可能变成预览和回读指针。后台继承了方法正文，也不等于写作者的新请求中已经包含正文。

影响：材料可能可访问却未被带入，也可能已带入但被错误归类。两种情况应分别诊断。

单独核对者实际能看到什么？

使用同一冻结模型，另建干净上下文，带入问题、当前候选稿、证据清单、方法正文和当前运行中选取的历史核对问题。

核对调用自身不开放工具，可以提出补读请求。当前构造核对输入时排除了候选稿整个 review 字段，只另行保留其中的 limitations；其中的 conflicts 因而没有一并带入。

它与写作者看到的内容并不完全一致。这种差异有些用于减少干扰，有些属于需要修复的信息缺漏。

当前最值得修复的交接断点

默认发布路径：核对完成后即可保存报告并结束，作者不会再获得一轮处理本次核对意见的机会。

已有可选路径：brief_review 可以先返回建议，作者再改稿或发布；但它还不是稳定的默认交接过程。

关联修订：可以继承证据与方法，但父稿正文和父核对意见不会自动作为完整交接包交给新作者。

当前问题不能全部归为上下文截断。例如现金流指标的正确名称和数值已经存在于材料中，正文仍然误用了指标。需要同时改善语义绑定和反馈处理。

建议：Recipe 记录研究，模型决定路径，原执行器承接动作

初始 Recipe 写目标、拟议步骤和检查方法；尚未执行的步骤不预填结果。后续根据发现增加、拆分、跳过或重访步骤。

Recipe 是所有阶段共用的工作记录，不是额外的执行器。 “核对 → 补查 → 分析 → 改稿”可以循环；简单问题可以合并步骤，资料不足可以交付边界清楚的部分成果。
1．创建：AI 写意图，程序绑定真实运行身份

AI 提出：研究问题、适用方法、拟议阶段、各阶段预期产出、如何检查，以及当前未知项。

程序负责：研究 ID、版本、冻结模型、授权范围、实际工具回执和产物指纹。AI 不能自行填写“下载成功”来替代真实回执。

2．取证：附件有来源，摘录有位置，覆盖范围单独记录

工具返回后登记原件引用、来源时间、文件指纹、实际返回的页码或文本范围。AI 再填写材料用途、适用期间、缺失内容与矛盾。

原件仍保存在现有工作区；Recipe 引用它，不复制出第二份资料库。报告所需的表头、单位和上下文应与数值一起提供，不能只给孤立数字。

3．分析与计算：事实、计算结果、推断分别留痕

重要结论关联主体、指标、期间、单位、来源位置及必要的计算。程序验证可以验证的算式与引用；语义关系仍由模型判断并接受核对。

例如“合同总额”不能仅因数值和引用都真实，就被当作“本年收入”。“计划拨付”与“实际到账”也应保留不同的状态。

4．每次交接：形成实际的模型输入包与可见清单

模型获得当前目标、工作单概览、适用方法正文、相关阶段产物、当前候选稿全文、必要原文及未解决问题，并可通过原工具继续读取完整材料。真实工具回执自动写入 Recipe；模型可选择阶段关联，不由程序猜测阶段目标已经完成。

程序记录本次请求包含的材料版本、正文或摘要、页码范围、省略项与输入指纹。索引和摘要用于定位，不能静默替代必要证据。

必须区分：已保存、工具已返回、已纳入本次请求。“已纳入请求”仍不代表模型已经正确理解。

5．核对：意见先返回作者，再由作者决定行动

核对者收到同版候选稿、关联证据、方法、已知矛盾和未解决问题；作者的自查结论只作为待核实说法，不能当作独立证据。

核对只看当前稿、证据和待检限制，排除作者“已修正”的自查记录；标题与开头单列，并留下“核心原句—原文—可证明范围”的对照，引用定位不代表语义正确。结果返回作者。收到新反馈时建立交接边界，其后完整保留连续操作、另存新稿及计算回执，不每步重置消息或用旧批次预览替代。作者可以采纳修改、依据原文不采纳、补读补算，或保留不确定性后交付。补读建议不应因为“核对不强制”就被丢弃。

建议式核对继续保留：不要求问题清零，不要求强制采纳。若正文修改，旧核对记录保留，并标明它对应旧稿。

6．发布与恢复：固定交付版本，保留真实状态

模型明确选择发布稿，程序关联该稿、证据和核对版本，再渲染 HTML。渲染器不替模型补写金融判断。

暂停、停止和退出在现有步骤边界保存工作单及已有成果；UNKNOWN 保持未知，不因工作单存在而自动重发。

不增加十分钟、最大轮数、搜索次数或“无进展即结束”门槛。Recipe 也不授权工具、不放宽工作区权限、不替代账户确认。沿用原数据库、工作区与执行器。

一张 Recipe 应记录什么？

顶层保存研究概览，各阶段引用独立产物。不必每轮把全部原始材料和完整历史重新塞进一张巨大 JSON。

部分应包含的内容主要责任
研究目标问题、对象、时点、方法、交付形式AI 提议，继承用户要求
阶段定义目的、依赖材料、预期产出、检查方式AI 可动态调整
真实执行工具调用 ID、实际终态、错误与产物引用原执行器登记
证据与判断原文位置、指标期间、算式、推断与反证AI 标注，程序校验可验证部分
上下文交接本次请求实际带入的版本、范围及缺项程序依据实际请求生成
核对与处置核对意见、作者处理、依据、遗留问题核对者与作者分别记录
最终交付发布稿版本、证据版本、报告位置与边界AI 选择，程序保存

示例：阻止现金流指标在交接时“换了名字”

以下为结构示意，不是已经实现的 API；原件版本、位置与回执均须以真实执行结果填写。

{
  "stage": "解释经营现金流变化",
  "purpose": "说明现金流与利润为何出现差异",
  "inputs": [{
    "artifact_ref": "现有半年报原件及其版本",
    "locator": "实际页码、表格与原文范围",
    "metric": "经营活动产生的现金流量净额",
    "period": "半年累计",
    "change": "-33.60%"
  }],
  "outputs": {
    "finding": "该变动对应经营现金流净额，不能直接称作销售收现变化",
    "open_questions": ["销售商品、提供劳务收到的现金是否另有变动"]
  },
  "checks": [
    "把指标名称、期间和百分比与同一原表对照",
    "检查正文是否把净额变化写成销售收现变化"
  ],
  "attachments": ["实际原文摘录引用", "计算回执引用"],
  "review": {
    "issues": ["正文存在指标错配"],
    "author_action": "回读原表并修改对应陈述"
  }
}
这个例子的价值不是多存一个百分比，而是把指标名称 → 原表 → 分析 → 正文 → 核对意见 → 作者修订连起来。仍然需要真实原文和模型判断，不能只检查字段是否填满。

“验收形式”应分三类记录

工程检查内容核对用户体验
原件是否取得、引用是否匹配、算式是否成立、HTML 是否保存。 指标是否一致、期间是否可比、因果是否有证据、关键疑点是否处理。 是否回答问题、是否容易理解、建议是否有条件、报告是否方便阅读。

三类结果分别记录。保存成功不代表金融结论正确；核对完成也不代表获得事实认证。

建议先做的最小闭环

先统一现有研究记录和阶段交接；补齐方法、父稿及历史问题的输入；将核对意见交回作者；增加实际模型输入清单。然后再按需要增加政策传导、估值敏感性等阶段。

新增阶段只声明自己的输入、产出和检查方法，复用原工具执行与交接机制，无须再建立一套调度系统。

当前交接还区分工作稿回读失败与此前快照：READ_FAILED 不代表模型已看到当前文件；材料清单明确标注缺失，模型可沿原工具检查。实际模型输出参数随运行冻结，单次输出截断与网络错误分别保留真实回执，不作为研究累计预算解释。

计算产物也区分原值与显示单位：比值先统一货币单位，0.15倍对应15%；程序核查算式和单位，不认证财务含义。真实稿件回放只用于工程验证，原稿和历史报告不自动改写。

规模覆盖不等于实际资金来源：分红所属盈利期、实际付款主体与时间、可动用资金分开核查；证据不足时保留来源未知。截止日之后的行情或新披露单列，不能进入该时点可知的估值与风险结论。作者和核对者都需要判断这些关系，Recipe与字段完整本身不认证结论。

实现依据：研究会话与证据注入 · 角色成果与Recipe映射 · 核对输入构造 · 循环与发布分发 · 通用批次调度

核对角色系统指令与作者执行流程分离：保留同一模型、原问题、方法及实际证据，不再把作者的研究启动与正文发布要求带入核对。作者按原目标判断核心缺口、收窄或发布，可选建议不会自动扩大用户要求；没有新增轮数收尾或意见清零门槛。
