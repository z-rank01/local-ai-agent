# Qwen 聊天上下文容量校准

| 项目 | 依据与处理 |
| --- | --- |
| 真实问题 | startup34原Web查询在约28872 tokens触发17条消息压缩，随后无进展保留原文；第三次报告读取后约31094 tokens又触发24条消息压缩，导致查询长时间等待 |
| 原因 | qwen3.8-flash静态模型未声明上下文，聊天容量函数按未知模型回退32768；股票专业执行输入窗口是另一份冻结配置 |
| 官方规格 | 2026-10-12核对[阿里云型号页面](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)：上下文1000000，思考模式最大输入983616、最大输出131072 |
| 修改 | 仅为确切型号和现有DashScope端点声明1000000上下文，并记录来源、核对日期；未知型号仍标保守回退，原有压缩阈值提供输出余量 |
| 范围 | 影响新聊天运行时的容量判断，不修改供应商参数、默认模型或已冻结股票任务；不删除原始消息及摘要证据 |
| 验收 | 超过旧32K的原文和末尾否定完整保留、不触发提前压缩；模型目录、容量及直连接口回归见本轮输出 |
| 尚未证明 | 尚未实际请求到100万token边界；官方容量声明不冒充极限负载通过。需唯一入口重载并复核页面查询体验 |
