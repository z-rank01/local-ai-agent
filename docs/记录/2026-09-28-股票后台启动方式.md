# 2026-09-28 股票后台启动失败：定位与改由启动器启动

> 当时状态：聊天侧与股票侧功能正常，但**页面无法开启股票技能**，`data/logs/stock-service.err.log` 反复报 SQLite 打不开库。
> 结论已落到 `AGENTS.md`（规则与排障顺序）和[日常运行指南](../日常运行指南.md)（用户可见行为）；本文保留证据与失败尝试。

## 最终原因

**股票后台由聊天后端派生时，子进程无法写入股票仓库。** 限制沿整棵进程树继承，与文件权限无关。

| 启动来源 | 结果 |
| --- | --- |
| 启动器 `Start-Process`（顶层进程） | ✅ 正常读写 `simulation/`，SQLite 正常 |
| 聊天后端 `subprocess.Popen`（子进程） | ❌ `PermissionError 13` → `sqlite3.OperationalError: unable to open database file` |

同一可执行文件（`.venv-paper\Scripts\python.exe`）、同一用户（`CHEN\Administrator`）、同一路径，唯一差别是**谁派生的**。

已排除的方向（均实测否定）：

| 假设 | 否定依据 |
| --- | --- |
| Windows 权限 / ACL | 仓库根与 `simulation/` 的 `icacls` 两边一致（`Authenticated Users:(M)`），无 DENY 规则；令牌为 Medium 完整性 |
| 令牌 / 身份 | 控制与网关令牌文件齐全，BFF 与后台同为用户进程 |
| 数据库损坏 | `PRAGMA integrity_check` 通过；stock venv 可 `rw` 打开，jobs 61 条完好 |
| 端口 / 路径 / 配置 | `daily-services.json` 无隐藏字符；绝对路径 `--state-dir` 手工启动成功 |
| WAL 残留 | 确为一个**独立的**真实故障（见下），清理后 `Store()` 能跑通，但后台仍无法由聊天后端派生 |

## 失败尝试（不要再试）

以下都从聊天后端（conda 解释器）发起，**全部失败**：

```
subprocess.Popen(列表)             cmd /c "…"                  cmd /c start "" /b …
写 .bat 再 cmd /c 该bat            powershell Start-Process …（由聊天后端调用）
```

`schtasks`（计划任务）被拒：`ERROR: Access is denied`，不能作兜底。

其中一次改动还引入了**用户可见故障**：把 `cmd /c start "" /b …` 以**列表**形式传给 `Popen`，`list2cmdline` 会把引号转义成 `start \"\" /b`，cmd 于是去找名为 `\` 的文件并弹出"Windows 找不到 '\' 文件"。已回退；教训是 cmd 内建命令的整条命令行必须以**字符串**传递。

## 另一个真实故障：WAL 锁文件残留

后台进程被强杀（`Stop-Process`、探针 `terminate()`、崩溃）后，`state.sqlite-shm` / `state.sqlite-wal` 会以不一致状态留在磁盘上，后续进程**读得动却写不进**：

```
unable to open database file            # 打开阶段
attempt to write a readonly database    # schema 写入阶段
```

处置：退出整个栈 → 删这两个锁文件（**不要碰 `state.sqlite`**）→ 重启。`-wal` 为 0 字节时删除无风险；非 0 时先整目录备份。本次据此恢复过一次，库本身未受损。
