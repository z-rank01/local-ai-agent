## 0. 结论先行

**判据**：一个"能力与质量优先"的实现，应当让模型拿到**一手事实**、能**翻页读完**、能**自主选择工具**，而把限制放在**真正不可逆或越权**的动作上。

**聊天仓库判定：偏"限制优先"，且多数限制打在读取面上，代价直接落在回答质量上。**

三个最重的问题（都已在运行配置下实测确认）：

| # | 问题 | 证据 | 后果 |
| --- | --- | --- | --- |
| 1 | `file_read` 只交付**前 8000 字符**且**没有翻页/偏移参数** | `core/tool_registry.py:23`、`core/tool_router.py:90-99`、`config/tools/file_read.yaml` | 用户本机数据实际只能看到 39%–42%，**且截掉的是最新交易日**。不是"限制手段"，是**能力缺失** |
| 2 | 云端模型可被**清空全部工具** | `core/agent.py:232-234`（`tool_defs = []`） | 一个开关关掉的是**整个工具面**，不是权限边界 |
| 3 | 质量规则用**超长祈使句 + 负例清单**表达，且与文档漂移 | `agent.py:238`、`02_analysis.txt`、`stock_bridge.py:305-370` | 挤占上下文、诱导模型转述而非核实、**代码里已成死代码却仍写在文档里** |

同时必须承认：**容器 + 路径双层封闭是真边界，应当保留**；真正该改的是**读取面与证据面**，不是拆掉隔离。

## 3. 逐项证据（关键处原文对照）

### 3.1 L1 —— 最重的读取限制，且**没有翻页**

工具定义只暴露 `path`：

```yaml
# config/tools/file_read.yaml
parameters:
  type: object
  properties:
    path:
      type: string
```

交付上限写死在注册表：

```python
# core/tool_registry.py:23
"file_read": 8000,
```

截断发生在路由层，且**只截 `content`/`stdout`/`stderr`/`output`/`text` 这几个顶层键**：

```python
# core/tool_router.py:90-99
max_chars = self._registry.get_max_result_chars(tool)
if max_chars and isinstance(result, dict):
    for key in ("content", "stdout", "stderr", "output", "text"):
        val = result.get(key)
        if isinstance(val, str) and len(val) > max_chars:
            result = dict(result)
            result[key] = (val[:max_chars] + f"\n...[已截断，仅显示前 {max_chars} 字符，共 {len(val)} 字符]")
```

`file_ops.read()` 本身**没有任何分页参数**（`skills/files/file_ops.py:80-118`），服务端也只有 `ReadRequest(path, encoding)`。

**实测代价**（本机真实用户数据）：

| 文件 | 尺寸 | `file_read` 实际交付 | 模型永远看不到 |
| --- | --- | --- | --- |
| `data/002594_daily.csv` | 19029 字符 | 8000 = **42.0%** | 剩余 58% |
| `data/600519_daily.csv` | 20341 字符 | 8000 = **39.3%** | 剩余 61% |
| `data/job_salary_prediction_dataset.csv` | 10008 字符 | 8000 = **79.9%** | 剩余 20% |

`600519_daily.csv` 共 321 行，可读窗口约到第 126 行——**最后约 60% 的交易日（越新的越看不到）从不进入模型**。文件按日期升序，所以被截掉的正好是最相关的近期数据。

模型只能靠 `code_exec` 写脚本间接绕（每次 print 又被压到 6000 字符），这是**用推理成本补偿一个缺失的参数**。

> 这是本次审查中**性价比最高的一个修复点**：给 `file_read` 加 `offset`/`line_range`，把上限提到远高于 8000（当前窗口 262144 tokens ≈ 65 万字符，8000 字符只用掉约 1.2%）。

### 3.2 L4 —— 工具自己说 50000，引擎只给 8000

```yaml
# config/tools/web_fetch.yaml（对模型可见）
max_chars:
  description: "最大返回字符数（默认20000，最大50000）"
```

```python
# core/tool_registry.py:28 —— 引擎层
"web_fetch": 8000,
```

服务端确实支持到 50000（`skills/websearch/app.py:158`），但路由层在返回前压到 8000。**模型被工具描述误导，且拿不到它以为能拿到的正文。**

### 3.3 L6 —— 超时口径三处不一致

| 层 | 值 | 位置 |
| --- | --- | --- |
| 策略（模型可被引导按此规划） | 300s | `config/policy.yaml:41` |
| 工具 schema 默认 | 120s / 60s | `runner/app.py:56,61` |
| 运行器环境封顶（**实际生效**） | 120s / 60s | `.env`、`docker-compose.yml:19-20` |

`policy_engine` 按 300 校验，`runner` 再 `min(req.timeout, _PYTHON_TIMEOUT)`。模型写 `timeout: 300` 能过策略、被静默压到 120 后超时——**一轮白费**。

### 3.4 L7 —— 一个开关关掉整个工具面

```python
# core/agent.py:232-234
if cloud and not getattr(self, 'workspace_cloud_allowed', config.WORKSPACE_CLOUD_ALLOWED):
    tool_defs = []
```

随后注入一段长说明（`agent.py:234`）。默认值 `False`（`config.py:116`）。

**当前实机状态是已授权**（`data/private/model-settings.json`：`workspaces["...data\\workspace"] = true`），所以现在云端可用工具。但设计上是"全有或全无"：没有"只读工具可授权、写入工具不授权"这类中间档。

### 3.5 L10 —— 长会话的压缩是有损的

```python
# core/context_manager.py:26-48（摘要提示词）
请将以下对话历史压缩为结构化摘要。严格按以下 5 段输出，每段不超过 200 字
...
# core/context_manager.py:148-149
if role == "tool" and len(content) > 300:
    content = content[:300] + "…"
```

在 157k token 之前不压缩（合理），但一旦触发，工具证据被砍到每条 300 字符、摘要每段 200 字。对"读了 3 份报告再对比"这类任务，**压缩即丢证据**，而模型不会知道自己丢过。

### 3.6 L11/L12 —— 记忆注入截断 + 合并缺陷（互为放大器）

```python
# core/memory_manager.py:35
_MAX_MEMORY_CHARS = 2000
# core/memory_manager.py:404-405
if len(content) > _MAX_MEMORY_CHARS:
    content = content[:_MAX_MEMORY_CHARS] + "\n...(记忆索引已截断)"
```

实测：`data/workspace/.memory/MEMORY.md` = **6124 字节**，注入只取前 2000 → **约 2/3 的记忆每轮都拿不到，且截掉的是文件尾部（最新条目）**。

合并逻辑只看首行标题：

```python
# core/memory_manager.py:159-172
heading = entry.splitlines()[0].strip() if entry.strip() else ""
if entry in base:   return existing
if heading in base: ...replace...
return base + "\n" + entry.strip() + "\n"   # 新标题 → 追加
```

于是写回模型只要换一个字（"…风险审计" / "…风险审计要点" / "…审计与修订方案"），就**不去重而是追加**。当前 MEMORY.md 里同一个"湖北正安-中控技术设备改造项目"就有 3 条近重复条目——**缺陷在自我放大 L11**。

### 3.7 L13 —— 用祈使句做质量保证

`agent.py` 每次请求都会往 system prompt 追加指令，例如：

```python
# core/agent.py:238
messages[0]['content'] += '\n执行任务必须通过本轮实际提供的工具调用，代码块本身不会执行。没有执行结果时不得声称已经读取、修改或生成文件。用户只要求讨论或只读时遵守该范围。'
```

```python
# core/agent.py:234（云端未授权时，约 200 字）
...不要声称正在查看或执行，不要编造文件内容，不要以未执行的代码代替任务完成...
```

再叠加 `02_analysis.txt` 的强制输出模板（"所有对比数据必须使用标准 markdown 表格"、"摘要控制在原文 20%-30%"、"必须严格遵守"）。

这类文本对**弱模型**有过拟合效应：模型会优先满足"格式与口吻约束"，而不是去补齐证据。同一条正确行为用**结构性手段**（更好的工具返回、可核对的字段）达成，成本更低。

### 3.8 L14/L15 —— 字符串黑名单：既挡不住，又伤合法任务

```yaml
denied_code_fragments: ["__import__", "eval(", "exec(", "compile(", "subprocess", "socket", "os.system", "os.popen"]
denied_shell_fragments: ["curl ", "wget ", "pip ", "apt ", "apt-get ", "docker ", "ssh ", "scp ", "nc ", "rm ", "mv ", "dd "]
```

- 子串匹配，不区分上下文：`x = "subprocess"`、变量名含 `socket`、注释里写 `exec(` 都会**直接拒绝**。
- `"rm "` / `"mv "` 会连带拒绝 `chmod`、`form `、`confirm ` 之类无关内容。
- 反向：`__import__("sub"+"process")`、`getattr(__builtins__, ...)` 轻松绕过——**挡不住有意绕过**。
- 沙箱注释自己说得很清楚（`skills/runner/sandbox.py:16-17`）："string-level rules are only supplementary"，真正的边界是容器。
- 而联网本来就通过 `web_search`/`web_fetch` 工具开放，`pip` 通过 `pip_install` 开放——**用片段黑名单挡 curl/pip 与既有工具面矛盾**。

结论：这些片段表**只降低模型的编码效率，不提升安全性**。

### 3.9 死代码：曾被认定为"在跑"的文件预取

`Agent._inject_context_into_messages`（`agent.py:414-432`）与 `_prefetch_file_context`（`agent.py:434-493`，含 `_PREFETCH_HINTS`、`_format_prefetch_content`）**从未被 `run()` 调用**——全仓库仅有的另一处引用是文档里注释掉的一行：

这是 `file_read` 之外**唯一**能把文件正文主动送进模型上下文的通路，现在是**死的**。它同时是 L1 的部分补偿——**复活它（并补云端门控）比加参数更快见效**。

## 5. 判定：偏"限制优先"

**证据一（权重最高）**：最影响答案质量的那个参数——`file_read` 的偏移量——**根本不存在**。系统在"少给数据"上做了三层截断（工具上限、路由截断、无分页），却在"多给数据"上没有对应投入，尽管窗口有 65 万字符余量。

**证据二**：安全策略被写成**字符串片段黑名单**，而代码注释自己承认它不是边界。安全成本付了（模型写代码处处受限），安全收益接近于零（容器才是边界）。

**证据三**：模型拿不到一手正文的地方，改用**超长祈使句**约束它的措辞（`stock_bridge.py:305-370` 一次性注入 6 段"不得声称…"；`agent.py:234/237/238/240`）。这是在**约束输出**而不是**补充证据**——质量问题的根源（看不到事实）没有解决，只降低了"说错话"的概率。

**反证（公允起见）**：容器的加固、软删除、自动 git 提交、`file_edit` 的哈希校验，都是"给自由 + 可回滚"的正确形态。所以问题**不是安全意识过剩**，而是**安全的着力点错位**：把成本加在读取面，而不是加在不可逆动作上。

### 5.1 两个仓库的对比

| | 聊天仓库 `local-ai-agent` | 股票仓库 `Stock_Agent_Workspace` |
| --- | --- | --- |

**含义**：股票仓库**可复制的部分是它的隔离与投影设计**（类型化投影 + 失败即转本地 + 为被限制的读者准备替代路径），**不可复制的是"不让模型使用它已读到的事实"**这一层。聊天侧应当学前者，而不是继续在读取面上做截断、在提示词里补祈使句。

### 7.1 实测的架构：三条互斥路由

关键模块是 `services/paper/observations.py` —— 它把每个结果**路由**到一条路径，三条互斥：

```python
# services/paper/observations.py:17,32-46
Route = Literal['cloud', 'local', 'direct']
...
class ObservationProjection:
    """A mutually exclusive answer route and its two separated payloads."""
    route: Route
    observation: dict[str, Any]
    detail: str
```

| 路由 | 谁能读 | 用途 |
| --- | --- | --- |
| `cloud` | 云端模型，**只能读白名单字段** | 解释小型公开观察 |
| `local` | 本地 Ollama（`gemma4:26b`，实测端口 **12434**） | 只读解释 F01 权威原文 |
| `direct` | 不经模型，确定性渲染 | F01 原文直接展示给用户 |

三道防线让这个设计很难被绕过：

```python
# services/paper/observations.py:6
Routing is derived from the stored job kind and status; model output cannot mark a result public.
# services/paper/observations.py:67
Missing, malformed or contradictory metadata fails closed to the local route.
# services/paper/observations.py:64
``detail`` is deliberately never parsed or copied into ``observation``.
```

F01 是本地只读渲染器，**天生不经过任何模型**：

```python
# services/agents/adapters/f01.py:1
"""F01 报告与表格展示：只读渲染本地账本与归档，不调用模型、不重算、不改写原值。"""
```

本地解释路径则把 F01 原文交给**本地**模型，且明确要求它不作事实断言：

```python
# services/paper/answer.py:3,23,178
本模块只把用户问题和 F01 已渲染的权威原文交给本地 Ollama 做只读解释。
'你是模拟盘的本地只读解释员。只能根据用户问题和“F01 权威原文”整理一段易读的中文答复。'
"""Allow only fact-free interpretation; F01 is rendered separately. ..."""
```

### 7.4 判定（修正）：隔离层能力优先，面向模型的质量策略限制优先

**本节初稿判定"股票侧明显更接近能力与质量优先"，该判定错误**——依据只有 `cloud-fields.json` 的规模，没有核实模型实际被允许**使用**什么。逐行核实后修正如下。

**仍然成立、值得复制的一面**：

1. **限制的是"谁能读"，不是"能读多少"** —— 白名单给的是带类型的真实数值（105 字段里 47 个数字/整数），不是砍掉细节的摘要。
2. **限制由代码强制，不靠提示词** —— `cloud_view` 是纯函数投影；`observations.py:6` 的 `model output cannot mark a result public` 与 `:67` 的 fail-closed 是结构性保证。
3. **为被限制的读者准备了替代路径** —— 云端读不到 F01 → 本地 Ollama 读；本地模型也不可信 → `direct` 确定性渲染。
4. **有真正的模型友好设计** —— `public_evidence.py` 是无损分页（excerpt 索引 + 签名游标 + `coverage_analyzed/coverage_total`），是仓库里最好的读取面。
5. **有过主动松绑的记录** —— 固定步数上限、24000 字符/100 事实/600 字符解释/8 缺口的旧上限已被移除（`broker.py:143-147`、`market_events.py:209-247`）；`research.py:185-187` 明确拒绝让数据缺口阻断只读研究。

**但三条反证推翻了初稿判定**：

1. **`answer.py:177-220` 的逐句事实删除**——系统把 24000 字符权威正文交给本地模型，然后删掉每一个含数字、枚举、裁决或评价的句子（`:214`），并在提示词里禁止复述（`:26`）。这是"限制优先"最强的单一证据：**模型不被允许使用它已经读到的事实**。代码注释（`:180-182`）诚实地承认 token 归属无法证明绑定正确——问题是真的，但选的补救是**删除模型的分析产出**，而不是**校验它**。
2. **一切事实枚举锁定 + 纯投影**——`cloud-fields.json`（657 行、16 类）+ `observations.py:296-299` 自述意图是"未来调用方也无法意外加入原始候选、私有材料、笔记或账户字段"。**安全靠构造，能力靠例外**。
3. **拒绝原因转发建好了却几乎没用**（S16，1/418）——机制存在，覆盖为零。这是"连补偿收益都没拿到的限制"。

**结论**：股票仓库的**边界设计**（谁能读什么、失败往哪转）是能力优先的；但它的**模型使用策略**（模型能用读到的东西做什么）是限制优先的。两者必须分开评价——初稿把前者当成了整体。

**股票侧最值得改的三处**（都不是拆安全边界）：

- **S10**：把逐句删除换成**后验溯源校验**——数字/枚举若出现在输出中，要求它出现在源文本里；不通过就只删该句并记 `answer_issues`。或只允许引用原文片段。这是本地路径唯一的高带宽读法，现在被压成不含事实的套话。
- **S16**：给 `master.py`/`ledger.py`/`research.py`/`jobs.py` 的约 417 处裸 `raise RuleError(` 补 `code=`，复用已有的 `REJECTION_CODES` 通道。机制已就绪，是纯粹的覆盖率工作。
- **S11/S13**：去掉静默抽样（改为真分页或全量），并把目录准入的**真实分母**（`catalog_total` vs `catalog_count`）返回，让"679 未深读"成为真话。

**次优先**：S15（`api.py:101` 的 13 步上限要么提高并返回 `STEP_LIMIT`，要么写进文档）、S5（简报元信息以结构化字段返回）、S3（`session_summary` 改为"枚举 + 受限模板"）、S8（要么 `model_budget_mode: "enforce"`，要么改文档）。

### 7.6 一个重要的"读取面"缺失：模型读不到任何一根 K 线
